# HarryListenly 听书应用 — 技术架构文档

基于 Next.js 的前后端一体移动端 Web 听书应用技术方案。

---

## 一、技术选型总览

| 层次 | 技术选型 | 说明 |
|------|----------|------|
| 框架 | Next.js 14+ (App Router) | 前后端一体、SSR/SSG、API Routes |
| 语言 | TypeScript | 类型安全、可维护性 |
| UI | React 18 + Tailwind CSS | 响应式、触控友好 |
| 状态管理 | React Context + Zustand（可选） | 全局播放状态、用户态 |
| 数据请求 | fetch / SWR 或 TanStack Query | 服务端/客户端数据拉取与缓存 |
| 音频播放 | HTML5 Audio 自定义封装 | 进度、倍速、后台行为 |
| 数据库 | MySQL | 专辑、节目、用户、进度、收藏等业务数据 |
| 存储 | 服务端 DB + 客户端 localStorage + 对象存储/文件存储（音频） | 进度、收藏、登录态；音频文件见下文方案 |
| 认证 | JWT 或 Session | 登录、鉴权（V0.3+） |

## 二、整体架构图

```
Client (Browser)

        | fetch / SWR / Server Components

  - App Router: /, /category, /search, /album/[id], /play, /me, /api/*

```

仓库采用 **apps 分离**：听书应用在 `apps/web`，管理后台在 `apps/admin`，文档在根目录 `docs/`。

## 四、核心模块设计

### 4.1 播放器模块（前端核心）

- 状态：当前专辑 ID、单集 ID、播放状态、当前时间、总时长、倍速、定时关闭、播放队列。
- 持久化：进度变化写入 localStorage 或 POST /api/progress（登录用户）。
- 能力：播放/暂停、seek、上一集/下一集、倍速、定时关闭、断点恢复。
- UI：底部迷你条 + 全屏播放页（大封面、进度、倍速、定时、列表）。

播放器状态示例（stores/player.ts）：

- albumId, episodeId, status(playing|paused), currentTime, duration, playbackRate, sleepTimer, queue
- 方法：setEpisode, play, pause, seek, setRate, setSleepTimer, saveProgress

### 4.2 专辑与节目数据模型

### 4.3 API 设计概要

- GET /api/categories — 分类树
- GET /api/albums — 专辑列表（分页、分类、排序）
- GET /api/albums/[id] — 专辑详情
- GET /api/albums/[id]/episodes — 节目列表
- GET /api/search?q= — 搜索
- GET/POST /api/progress — 续听进度
- GET/POST/DELETE /api/favorites — 收藏（需登录）
- GET/POST/DELETE /api/history — 历史（需登录）
- POST /api/auth/login, /api/auth/register — 登录注册

### 4.4 数据层与存储

- **数据库**：统一使用 **MySQL**。ORM 可选 Prisma 或 Drizzle；开发阶段可用同一 MySQL 或 Docker 起 MySQL。
- **业务表**：用户、分类、专辑、节目、播放进度、收藏、收听历史等均存 MySQL；节目中 `audio_url` 存音频访问地址（由下方音频存储方案提供）。
- **缓存**：Next.js 对专辑/节目接口做 revalidate 或 ISR，减轻 MySQL 压力。

## 五、前端技术要点

- 移动端：viewport、Tailwind 移动优先、底部 Tab + 播放条固定、触控区域足够大。
- 音频：HTMLAudioElement 或 useAudio hook，统一管理 src、currentTime、playbackRate、ended（自动下一集）；注意 Safari 自动播放策略。
- 性能：长列表虚拟滚动、Next/Image 图片懒加载、首页用 Server Components 减客户端 JS。

## 六、安全与鉴权

- 登录返回 JWT；需鉴权 API 校验 Authorization: Bearer &lt;token&gt;
- Token 存 localStorage 或 HttpOnly Cookie
- **协议**：若不担心音频被公开访问，**可使用 HTTP** 提供站点与音频；HTTPS 非必须，见下文「HTTP 方案」。

## 七、音频文件存储方案

**当前策略**：**先使用本地磁盘方案，后续再迁移到 OSS**。音频体积大、需支持流式播放；若不担心音频被公开访问，可直接用 **HTTP** 提供音频 URL。以下方案均可使用 HTTP 或 HTTPS。

### 7.0 使用 HTTP 方案（音频可公开时）

- **可以**：整站与音频均使用 **HTTP**，不配置 HTTPS、不做签名 URL、不做 Referer 防盗链。
- **做法**：`episode.audio_url` 存普通 HTTP 地址即可，例如：
  - 本地：`http://your-server/audio/album1/ep1.mp3`
  - 对象存储：使用该存储服务提供的 HTTP 外网地址（多数云厂商同时提供 HTTP/HTTPS）。
- **注意**：若将来页面改为 HTTPS，浏览器会要求音频也走 HTTPS（混合内容限制），届时再把音频改为 HTTPS 或相对路径即可。
- **结论**：不担心公开时，HTTP 方案简单够用，无需额外鉴权与证书。

| 方案 | 适用阶段 | 优点 | 缺点 |
|------|----------|------|------|
| **本地磁盘 + Next 静态/接口** | **当前采用**，开发与内测 | 零成本、部署简单、易迁移 | 扩容差、无 CDN |
| **云对象存储（OSS/S3）** | 后续迁移目标 | 可靠、按量付费、可配 CDN | 需配置存储与域名 |
| **对象存储 + CDN** | 大流量生产 | 就近访问、省带宽 | 需配置 CDN |
| **自建 MinIO / NAS** | 内网或自建机房 | 数据自主、S3 兼容 | 运维与带宽成本 |

### 7.1 方案一：本地磁盘（当前采用，便于后续迁 OSS）

- **存放位置**：音频文件放在项目 `public/audio/` 或服务器指定目录，通过 Next.js 静态资源（`public/audio/...` 自动映射为 `/audio/...`）或 Nginx 提供 **HTTP** 访问。
- **MySQL 存储建议（便于迁移）**：`episode.audio_url` 存**相对路径**，例如 `/audio/album1/ep1.mp3`，**不要**直接存带域名的绝对 URL。播放时由 API 或前端根据环境变量 `AUDIO_BASE_URL`（如 `http://localhost:3000` 或 `http://your-domain.com`）拼成完整 URL；未配置时默认用当前站点 origin。这样后续迁 OSS 时只需改为「OSS 的 base URL + 同一相对路径或 OSS key」，无需改库里的历史数据逻辑。
- **目录约定**：建议按专辑分目录，如 `public/audio/{albumId}/{episodeId}.mp3` 或 `public/audio/{albumId}/ep_{order}.mp3`，与相对路径一致。
- **优点**：实现快、零依赖、可直接 HTTP 播放；相对路径设计方便后续一键切 OSS。**缺点**：无法水平扩展，不适合公网大流量，迁移前可一直用本地。

### 7.2 方案二：云对象存储（后续迁移目标）

- 使用 **阿里云 OSS**、**腾讯云 COS**、**AWS S3**、**七牛云** 等，将音频上传到 Bucket，获得永久或长期有效的文件 URL（云厂商一般同时提供 **HTTP** 与 HTTPS 地址，可只选 HTTP）。
- MySQL 只存「最终可访问的 URL」（或存储 key，由 API 拼 URL）；**无需鉴权时直接存公开 HTTP 地址即可**。
- **上传方式**：后台管理端直传（前端传签名或后端代传均可）；或服务端脚本批量导入。
- **优点**：持久化、多副本、按量计费；公开 HTTP 即可，无需签名与防盗链。**缺点**：直接暴露 Bucket 域名时可能产生外链流量费用，可按需再配 CDN。

### 7.3 方案三：对象存储 + CDN（大流量生产）

- 对象存储作为**源站**，前面挂 **CDN**（阿里云 CDN、腾讯云 CDN、Cloudflare 等）。
- 音频 URL 使用 CDN 域名，可用 **HTTP**（如 `http://cdn.yourapp.com/audio/xxx.mp3`）或 HTTPS；不担心公开时无需鉴权。
- **防盗链 / 鉴权**（仅在你需要时再做）：
  - **Referer 白名单**：仅允许自己站点域名请求。
  - **URL 鉴权**：服务端生成带签名的临时 URL。你当前场景可省略。
- **优点**：就近访问、省带宽、首包与 seek 更快。**缺点**：需配置 CDN；若仅 HTTP 且不鉴权，配置相对简单。

### 7.4 方案四：自建 MinIO / NAS

- **MinIO**：S3 兼容，可部署在自有服务器或内网，Next 通过 SDK 上传/生成预签名 URL。
- **NAS / 文件服务器**：音频放在 NAS，通过 Nginx 等提供 HTTP 访问或反向代理；适合内网或小团队。
- **优点**：数据完全自控。**缺点**：需自己保障可用性与带宽，公网多用户时成本较高。

### 7.5 选型与落地建议

- **当前阶段**：**先使用本地磁盘**。音频放 `public/audio/`，MySQL 存相对路径（如 `/audio/{albumId}/{episodeId}.mp3`），通过 `AUDIO_BASE_URL` 拼完整 URL，HTTP 提供播放。
- **后续迁移**：迁到 OSS 时，将音频上传至 Bucket，MySQL 可继续存相对路径或改为 OSS key，由服务端按「当前存储类型」拼出最终 URL（见 7.6）。
- **环境变量**：现阶段只需 `AUDIO_BASE_URL`（可选，默认用当前站点 origin）。迁 OSS 后增加 `OSS_BUCKET`、`OSS_REGION`、`OSS_ACCESS_KEY` 等；若用 CDN 可加 `CDN_DOMAIN`。

### 7.6 后续迁移到 OSS 的步骤

1. **数据结构**：保持 `episode.audio_url` 存**相对路径**（如 `/audio/album1/ep1.mp3`）或改为存 OSS **object key**（如 `audio/album1/ep1.mp3`），便于同一套逻辑兼容本地与 OSS。
2. **服务端统一拼 URL**：在返回节目列表/详情的 API 中，根据配置或环境变量判断当前存储类型（`local` / `oss`），拼出最终可访问的音频 URL：
   - 本地：`AUDIO_BASE_URL + audio_url`
   - OSS：`OSS_PUBLIC_BASE_URL`（或 CDN 域名）+ `audio_url` 或 key。
3. **迁移动作**：将 `public/audio/`（或现有磁盘目录）下的文件批量上传到 OSS，保持路径与 MySQL 中一致；然后切换环境变量为 OSS，重启服务即可。
4. **可选**：在 MySQL 增加字段如 `audio_storage`（`local` / `oss`），按条目标记来源，便于灰度或回滚。
